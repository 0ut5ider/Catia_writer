# CATIA V5 (.catpart/.catproduct): open-source and publicly documented readers

- Date: 2026-09-06
- Role: web research agent (no code written)
- Question: what open-source or publicly documented code READS (ideally WRITES) CATIA V5 native files, and what does it teach us about generating our own files?
- Model: claude (via opencode session), research harness: GitHub API (authed code + repo search), raw.githubusercontent fetches, DuckDuckGo/Bing/Wayback, PRONOM, vendor pages.

## Verdict (one paragraph)

There is one serious open-source CATIA V5 reader: **cadmpeg** (Rust, Apache-2.0, docs CC-BY-4.0). It is a clean-room project with a full public reverse-engineered `.CATPart` format spec, a machine-checked byte-layout table, a working container + partial geometry decoder, and a published list of everything still unknown. **No open-source project writes native .catpart or .catproduct. None exists.** Public OCCT cannot read catpart at all (its public `src/DataExchange` tree contains no CATIA toolkit; CATIA readers are the closed commercial "Data Exchange" module). FreeCAD has no direct importer (zero catpart references in the repo; users convert via STEP/IGES or commercial converters). ASSIMP and VTK have no CATIA support (verified by code search across each repo). pycatia is COM automation, not file-format access. The rest of the open landscape is container-level tooling: PRONOM/DROID/file-magic signatures (OGL-licensed, exact magic `V5_CFV2\0`), version-tag readers, one C# script that scrapes component file names out of `.catproduct` as text, and cloud-convert wrappers (Onshape/Forge/Omniverse) that call closed decoders.

## What cadmpeg's spec teaches a future writer

The spec (CC-BY-4.0, `docs/formats/catia.md` + machine table `docs/layouts/catia.toml`) is the most complete public description. Verified highlights:

1. **Container**
   - Offset 0: magic `V5_CFV2\0` (`56 35 5F 43 46 56 32 00`... PRONOM bytes: `56 35 5F 43 46 56 32 00 00 * .CATPart`). KaiUR's script also records a `V5_CFV4` magic variant.
   - `0x08`/`0x0C`: big-endian `directory_offset` and `directory_length`; `dir_off + dir_len == file_size` (directory sits at EOF).
   - Trailing region: `CATIA_V5 CB0001\0` stream directory ending in `CB__END`; descriptors carry logical stream length at +0x0C, extent count at +0x50, then 20-byte extents (physical offset/length, BE, relative to the inner magic). This is the "Open Catalogue" store Dassault inherited from CATIA V4's catalogue concept.
   - A **nested inner `V5_CFV2`** sub-container holds fragmented named logical streams (`MainDataStream`, `SurfacicReps`, `Data`, ...) with the same directory grammar.
   - `FINJPL␠␠` (8 bytes + two spaces) marks named segments. Type word `0x01010003` = project-flags segment: contains `LastSaveVersion` summary wrapped in `<Version>…</Version><Release>…<ServicePack>…<BuildDate>…<HotFix>` ASCII tags, an embedded JPEG preview (`ffd8…ffd9`), and external-reference atoms (`CATStorageProperty`/`CATUnicodeString`/`CATIA` + target path ending `.CATPart/.CATProduct/.CATShape/.cgr`).
   - Document type is distinguished by the embedded ASCII filename in the header (same magic for part/product/drawing; PRONOM encodes exactly this).
2. **Identity model**: three separate identity layers: allocation (file-global object journal: `0x60` row tags, positional vertex ids, `b5 03` / `e5 0d 03` object ids), occurrence (face-local loop members, support/pcurve occurrences), and geometric definition. A writer must reproduce this separation or CATIA-facing consumers mislabel objects.
3. **Geometry (standard-nested band)**: FBB face rows; 15-byte `05 08 01` vertex rows (mm floats); `00 33 <kind>` surface markers; edge-row tables with selectable `u8/u16be/u24be` widths; `0x60` curve-support rows; alternative storage families: E5 `0D 03` record streams, zero-entity `a9 03`, float-packed `b5/a8` object streams. NURBS uses a three-way storage-class split (`a5 03 34/32/20`, `a8 <flag> 34/32/20`, `a9 03 34`). Appearance: `EB 01 R G B` and `EC 03 R G B A` packets.
4. **Six storage variants** (standard-nested, FBB-only, E5, zero-entity, float-packed, inner-no-directory) with detection rules; a writer targeting CATIA acceptance realistically must emit the standard-nested variant only.
5. **What is NOT known (their open-items ledger, CR-/DI- ids)**: extent-flags bit meanings; the design/feature "schema-program" semantics (`CATFeatCont`/`CATPrtCont` relation to history); inline `7C09` reference roles; relation result binding; release-band envelope. A writer must invent or re-derive all of the design-intent layer; nobody has published it.
6. **Discipline to copy**: cadmpeg derives everything from legally held files plus public information; decompiling CATIA binaries and SDK-derived constants are forbidden (LEGAL.md); decoder changes need byte-backed provenance; fuzzing and golden corpus (`corpus/` with CC0 donations). That model is directly reusable for our own RE work.

## Confirmed negative results (searched, absent)

- Public OCCT: no CATIA reader/writer; no `FA_CATIA`/`CatiaTo_occ` source in the repo (those names belong to the commercial Data Exchange product). CATIA V4 support is likewise not in public OCCT.
- FreeCAD: no direct import of catpart (zero references in repo). Only STEP/IGES/BREP via OCCT; `data/tests` has one STEP file that mentions CATIA.
- ASSIMP: no catpart importer (repo-wide grep clean). trimesh/pyvista therefore cannot read catpart natively either.
- VTK: no CATIA code.
- Upstream `file/file` magic: no CATIA entry (only third-party magic files carry `V5_CFV2`).
- GitHub: no `libcatia`, no `catia-reverse`, no "Open Catalogue" project, no CATIA V4 `.model` reader, no `.cgr` reader, no `.catshape` parser.
- Writers: searched "catpart writer/encoder/generate", "write catpart", "catproduct generator": nothing. The only way to *produce* native files today is running licensed CATIA (pycatia/CAA/COM), buying a commercial SDK's writer (CAD Exchanger does native), or feeding interchange formats (STEP/IGES/3DXML) that CATIA imports.

## What we can learn / recommended path for our own file generation

1. If "our files" means *files CATIA opens*: write STEP AP214/AP242 (import is universal) or 3DXML (Dassault's documented XML/zip format; open parsers already exist). Native catpart generation from open code is currently research, not a solved problem.
2. If we attempt native catpart: start from cadmpeg's spec and layout table; target the standard-nested variant; reproduce the container invariants (BE directory words, `CB0001`/`CB__END`, FINJPL segments, `LastSaveVersion` ASCII tags); treat feature history as out of scope initially (a model-less B-rep-only CATPart may still be rejected by CATIA; even cadmpeg stops at L1/L2 and lists the feature layer as unknown). Validate by byte-diffing our output against files we authored in a licensed CATIA.
3. For assembly-level metadata only (BOM/paths/placement extraction), the container is friendly: component paths are ASCII strings (`CATOctetArray` region in `.catproduct`), version tags are regex-able ASCII.
4. For detection: use the PRONOM byte sequences (OGL): catpart `56355F434656320000*2E43415450617274`, catproduct `56355F434656320000*2E43415450726F64756374`, catdrawing `56355F4346563200*434154447277436F6E74`.
5. Do not trust the WpfHexEditor whfmt prose; its signature bytes contradict three independent sources.

## Gaps

- No independent open re-implementation cross-checks cadmpeg's claims (single point of failure for open format knowledge).
- `.catproduct` semantics (placements, constraints/connections) are not documented anywhere openly; only the referenced-filename strings are trivially readable.
- Release-band coverage (V5R8→2024, plus `V5_CFV4`) is open; the spec admits it.
- No open writer exists, so byte-level *write-side* constraints (checksums? ordinal allocation? stream naming UUIDs formatting: `<w1:x>_<w2:08x>_<w3:x>`) are only partially known (cadmpeg records the naming format but not generation rules for every field).
- Encrypted/controlled files are out of scope by policy in every clean-room project.
